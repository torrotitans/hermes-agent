# Execution Plan: Layer 0 - Presentation (Omni-Channel Gateway)

## System Context for 7B Model
**Role:** You are the execution agent tasked with building Layer 0 of the Torro Agent Architecture.
**Goal:** Implement the Omni-Channel Gateway, a headless cognitive core interface supporting CLI, Web, Slack, and Outlook adapters.
**Invariants to Enforce:** 
- NO RAW SQL.
- Must use SQLModel for any DB connections.
- Strict Least Privilege.
- All code must include `FN:` prefix in docstrings.
- Files must be <200 lines. Use descriptive variables.

---

## Phase 1: Conversational UI Core
**Token Estimate:** ~1M Tokens
**Objective:** Scaffolding the primary terminal/web interfaces and the interactive logic clarification loop.

### Task 1.1: Scaffold Standard CLI/Web Interface
**Token Budget:** 150k Tokens | **Time Estimate:** 5-10 Minutes
**Inputs Needed:** `agentic/standard/AGENT.md`, `agentic/standard/UI.md`
**Action Steps:**
1. Create `engine/presentation/cli/main.py`.
2. Implement an Ink/React-style terminal UI using `rich` or `textual` in Python.
3. Establish the base application loop that prompts the user for input without processing logic.
4. Apply the Torro Principle 5: Include an ASCII Banner at the primary entry point.
**Acceptance Criteria:** `python engine/presentation/cli/main.py` renders a banner and an input prompt successfully without crashing.

### Task 1.2: Implement Mode Selection Menu
**Token Budget:** 150k Tokens | **Time Estimate:** 5-10 Minutes
**Inputs Needed:** `engine/presentation/cli/main.py`
**Action Steps:**
1. Extend `main.py` to intercept the first user input and present a mode selection menu.
2. Define exact options: 1. Plan, 2. Gap Analysis, 3. Root Cause Analysis, 4. Execute.
3. Route the user's selection to a placeholder handler function in `engine/presentation/handlers.py`.
**Acceptance Criteria:** The UI displays the 4 modes and correctly logs the user's selection with the `FN:handle_mode_selection` prefix.

### Task 1.3: Logic Clarification Loop
**Token Budget:** 150k Tokens | **Time Estimate:** 5-10 Minutes
**Inputs Needed:** `engine/presentation/handlers.py`
**Action Steps:**
1. Create `engine/presentation/clarification.py`.
2. Implement a `ClarificationManager` class. Add `FN:ask_clarifying_questions` to the method docstring.
3. This class must take the user's initial prompt and determine if it is ambiguous (mock this logic for now by returning 2 hardcoded questions).
4. Integrate this manager into the `Execute` and `Plan` mode handlers.
**Acceptance Criteria:** Before executing a mock plan, the CLI prompts the user with 2 follow-up questions and waits for responses.

## Phase 2: Enterprise Integration Adapters
**Token Estimate:** ~1M Tokens
**Objective:** Build asynchronous approval mechanisms via standard enterprise channels.

### Task 2.1: Implement Slack Adapter
**Token Budget:** 150k Tokens | **Time Estimate:** 5-10 Minutes
**Inputs Needed:** `config.ini` (mocked)
**Action Steps:**
1. Create `engine/presentation/adapters/slack_adapter.py`.
2. Define a `SlackAdapter` class with `FN:dispatch_approval_message`.
3. Read the Slack Webhook URL from `config.py` (which reads from `config.ini` per Principle 11).
4. Implement a POST request to dispatch an interactive block (Approve/Deny) to Slack.
**Acceptance Criteria:** The script successfully constructs a valid Slack Block Kit JSON payload and handles network timeouts gracefully.

### Task 2.2: Implement Outlook Adapter
**Token Budget:** 150k Tokens | **Time Estimate:** 5-10 Minutes
**Inputs Needed:** `config.ini` (mocked)
**Action Steps:**
1. Create `engine/presentation/adapters/outlook_adapter.py`.
2. Define an `OutlookAdapter` class with `FN:dispatch_email_approval`.
3. Use Python `smtplib` and `email.mime` to construct an approval email with embedded mailto: reply links for Approve/Deny.
4. Ensure no credentials are hardcoded. Read all settings via `app.config.from_object`.
**Acceptance Criteria:** The adapter correctly formats the MIME multi-part email and initiates an SMTP connection (using a mock server for testing).
